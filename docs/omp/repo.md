# Repo：企业项目代码定位指南 {#repo-guide}

Repo 为当前项目建立本地代码索引，用来反复定位实现、错误信息、配置键和 Python 定义。它先给出候选位置，AI 再读取当前源码继续调查，不直接给出调用关系或修改影响结论。

尚未启动 OMP，可先看 [OMP 快速指南](/omp/)。企业文档资料使用 [Wiki](/omp/wiki)，方案讨论使用 [Team](/omp/team)；自有能力概览见 [功能说明](/omp/features)。

## 1. 先分清 Repo 与 Wiki {#repo-or-wiki}

- **Repo 查项目代码。** 纳入源码、测试、配置及其他可索引文本，记录相对路径、类别、原始行号和文本内容；Python 另有定义定位。
- **Wiki 查 Markdown 资料。** 需要单独导入和维护，适合规范、设计说明及操作手册。Wiki 数据库与 Repo 数据库、命令完全分离。
- Repo 中的“源码／测试／配置／其他”是文件类别，不是测试覆盖、配置消费关系或依赖分析。

Python 定义定位支持模块、类、函数和方法，返回位置、限定名与可用签名。同名定义通过路径、限定名和行号区分。

它支持 Python 3.6 风格的装饰器、嵌套定义和异步函数，也兼容该版本在合法同步上下文中使用的 `async`／`await` 标识符。无需改造源码、补写类型或安装语言服务器，但不做名称绑定、引用解析或类型推断。其他语言主要提供文本候选。

## 2. 确认项目范围和数据隔离 {#scope-and-storage}

建库前先确定“这一次要索引哪个项目”：

- **Git 项目：** 使用当前 worktree 的根目录。从子目录启动，也会覆盖整个 worktree，不是只索引该子目录。
- **非 Git 项目：** 使用启动时的当前工作目录。目录过大会带来额外扫描和维护成本。
- 数据库按规范化后的项目根目录与用户 profile 隔离。不同 worktree 不混用内容；换 profile 或数据根后，也不要假定原索引仍在当前范围。

在**系统终端**中，进入目标项目后启动 OMP；需要独立 profile 时可用：

```sh
omp -P project-a
```

`-P` 是 profile 选项，不是小写 `-p` 的非交互模式。普通启动也可以，关键是后续使用同一预期 profile。

默认数据库位于用户 profile 数据目录，不向源码目录写库。已有部署也允许数据库与 NFS 代码库共置；源码本身可以全部位于 NFS。Repo 不要求为了 offline 将数据库搬入共享内存，也不提供 NFS 专用搬迁命令、缓存服务或跨用户共享索引。

如部署已使用 `OMP_CONFIG_ROOT`，它统一影响 OMP 数据根，包括 Repo、Wiki、会话和日志，不是 Repo 专用设置。不要为找回索引随意修改数据根；先核对启动环境与 profile。

**可以共置不等于已经验证多机并发安全，也不等于公司 NFS 一定更快。** 建库与维护仍需读取项目文件，网络文件系统的实际成本要在对应环境判断。

## 3. 首次建立索引 {#first-build}

以下命令输入到 **OMP 输入框**，不是系统终端：

```text
/repo
```

1. 查看面板的 `Root:`，确认是预期项目或 worktree。路径很长时检查折行后的完整尾部。
2. 尚无索引时按 `b`，进入建立确认。
3. 再核对确认画面的目标根目录，按 `y` 开始；按 `n` 或 `Esc` 放弃这次确认。
4. 等待进度结束，检查文件数、符号数及覆盖状态。出现失败或未核对提示时，先处理原因，不把“有结果”当成完整建库。
5. 按 `Esc` 关闭面板，回普通对话描述任务。

首次建立必须由用户确认。AI 的只读查询不会自动建库。**不存在 `omp repo ...` 系统终端命令组。**

### 面板操作速查 {#panel-controls}

- `b` → `y`：尚无索引时建立。
- `u`：更新，即对当前范围做完整核对，不需要再按 `y`。
- `r` → `y`：重建，适用于重新解析或恢复损坏、不兼容数据库。
- `d` → `y`：删除当前范围的索引，不删除或修改源码。
- `c`：取消正在进行的建立、更新或重建。
- `Esc`：关闭；操作进行中会先询问是否取消并关闭，`y` 确认，`n` 或 `Esc` 返回。

建立、重建和删除均应先核对确认画面中的根目录。删除期间如有在途建库，程序会先取消并等待其结束，避免删除后又发布索引。

### 状态字段怎么读 {#status-fields}

- `Files` / `Symbols`：当前索引文件数与 Python 符号数，不代表全部项目文件都能纳入。
- `Generation`：已发布的索引代次；更新结果按代次提供一致视图。
- `Coverage`：覆盖情况。`incomplete` 表示不完整，`unchecked` 表示仍未核对；需要完整核对的提示不能忽略。
- `Pending`：已知待处理路径。数量后的 `+` 表示展示有界，并非只有面板列出的几项。
- `Failures`：失败数与原因，例如读取或 Python 解析失败。
- `Last full check`：最近一次完整核对成功时间；`never` 表示尚无成功记录。它不证明此后没有外部修改。
- `Exclusions`：排除信息，帮助解释文件为何未进入索引。

## 4. 用自然语言让 AI 定位 {#ask-ai}

建库后不必逐次记忆工具参数。在 **OMP 普通对话输入框**描述目标即可，例如：

```text
用 repo 找读取配置和处理 timeout 的代码候选，范围先限制在 src。
读取当前命中文件，解释正常路径与错误处理；不要仅凭索引片段下结论。
```

```text
定位 Python 类 ConfigLoader 和它的 load 方法。
区分同名定义，给出文件与行号，读取当前源码后解释参数和返回值。
```

```text
检查 Repo 覆盖状态。若存在未核对、待处理或解析失败，先说明缺口，
再找 tests 目录里与配置加载有关的候选，不把类别当成覆盖证明。
```

AI 使用一个只读 `repo` 工具，只有三种动作：

- `search`：默认动作。搜索普通文本，返回文件、类别、原始行号范围和有界片段。
- `symbol`：按 Python 名称或限定名称定位定义，返回位置与可用签名。
- `status`：查看根目录、代次、覆盖、待处理路径及失败；**不扫描源树，也不触发完整核对**。

### 工具参数示例，不是终端命令 {#ai-query-parameters}

下面 JSON 是 **AI 调用 Repo 工具的参数**，不要粘贴到 shell，也不是 `/repo` 面板命令：

```json
{ "query": "timeout", "path": "src" }
```

```json
{ "action": "symbol", "query": "ConfigLoader.load", "path": "src" }
```

```json
{ "action": "status" }
```

工具仅接受 `query`、`action`、`path`、`cursor`。不提供类别筛选、页大小、建立、更新、重建或删除参数。省略 `action` 与显式 `search` 等价。

某些会话将 Repo 按需提供为 `xd://repo` 设备：AI 先读设备说明，再携带 JSON 查询；另一些配置直接显示顶层 `repo` 工具。即使设备通过 `write` 传参，Repo 查询仍是只读，不因此获得修改源码或管理索引的权限；自身审批策略仍有效。

## 5. 读候选、缩小范围、继续翻页 {#results-and-pagination}

文本搜索是不区分大小写的字面量检索，不是正则或 SQL。完整边界匹配优先，其次子串，拆分词元可补充召回，例如 `timeout` 可以找到 `ERR_TIMEOUT`；不足三个字符也有匹配路径。Python `symbol` 对名称和限定名做大小写不敏感的子串定位。

每页固定**最多 20 条**，不是最多只有 20 个候选：

1. 先根据路径、类别和片段挑候选，不只看第一条。
2. 若有后续游标，让 AI 保持动作、查询词和路径，用返回的 `cursor` 继续；不要自行拼造游标。
3. 如索引代次变化，旧游标不再适用，重新从第一页查询。
4. 需要覆盖细节时单独查询 `status`，搜索页不会反复打印全部根目录、排除清单和核对时间。

`path` 是**索引根内的相对文件或目录路径**，如 `src/config`、`tests`，不是任意磁盘路径。可使用 Windows 分隔符；`.`、重复分隔符及不越界的 `..` 会归一化。POSIX 上若确有含字面反斜杠的对应路径，会优先按该路径处理。

不要传绝对路径、盘符相对路径或越过根目录的 `../`；非法范围应报错，不是正常零命中。缩小目录后仍不明确，可换更具体的错误文本、配置键或 Python 限定名继续搜索。

**原始行号指向该索引代次保存的原文。** 当前文件可能已经变化，编辑前必须重新读取。无索引、正常零命中和查询错误是三种不同情况，都不能推导为“仓库没有这段代码”。

### 与其他工具怎样配合 {#tool-division}

- 已知文件的小改动：直接 `read` 当前文件，不必强制经过 Repo。
- 找文件名或路径：用 `glob`；语义检索 `find` 不是文件名 glob。
- 找名称的全部文本出现位置或正则：用 `grep`，同时检查范围、错误和截断。Repo 不保证找全所有出现位置。
- 找定义、引用、调用方或重命名：结合可用 LSP 与当前源码；Repo 本身不依赖 LSP，也不要求额外安装语言服务器。
- 找某种语法写法：可用时使用只读 `ast_grep`。结构化修改属于另外的 `ast_edit` 能力，应先读对应设备说明，不是 Repo 查询。
- 最终正确性：阅读实际修改、运行任务所需的测试；索引命中不能代替测试结果。

## 6. 变化后何时更新，何时重建 {#update-or-rebuild}

**已知 OMP 文件变化会局部维护。** 成功的编辑、新建、删除和重命名会记录路径，包含 LSP 实际落盘及回滚；下次 `search` / `symbol` 前合并处理。重命名跟踪旧、新路径；预览、拒绝和未执行操作不算落盘成功。

**以下情况不要依赖自动发现：**

- bash / eval 实际执行后会标记可能受影响范围未核对；设备入口、执行后异常、超时、中断及后台任务结束也在通知范围内。程序不会靠命令文本猜出全部修改。
- 切换分支、会话启动或切换、Git HEAD 及工作区线索可能产生未核对提示。Git 提议的候选路径不等于完整核对。
- 在外部编辑器修改、批量新增或删除、修改 `.ignore` / `.gitignore` 等范围规则，不保证下次查询即时发现。
- 内建 Git 命令启动改动工作树的步骤后，也会标记未核对；纯只读状态操作不等同改树。

需要当前范围的完整核对时，回 `/repo` 按 `u`：枚举并读取纳入范围的文件，通过内容指纹发现新增、修改和删除。同大小、同时间戳的变化及可纳入的未跟踪新文件也会核对；内容没变的文件不重复解析。

**更新与重建不是一回事。** 更新复用未变内容的记录；重建重新建立完整索引。升级解析器后，旧库已有的 Python 解析失败或缺失符号，可能因内容指纹未变继续被更新复用，必须按 `r` → `y` 重建重新解析。损坏或 schema 不兼容也走重建恢复。

`Pending`、`unchecked` 和失败提示都意味着存在缺口。最近完整核对成功只说明当时的状态；即使没有线索，也不能证明之后没有外部变化。需要穷尽或当前事实时，仍要回到文件系统与现有工具。

## 7. 取消、失败和纳入边界 {#failure-and-inclusion}

建立、更新、重建失败或取消时，不发布半成品，保留原有可用代次，并报告未核对状态。首次建立失败则没有可用旧代次。不要把“仍然查得到旧结果”误判成维护成功。

完整核对发布前还会核对文件指纹与清单。扫描中发生未通知的修改、新增或删除，可能导致本次核对失败并保留旧代次；应等文件树稳定后再完整核对，而不是清除提示继续使用旧结果。

索引范围还有这些限制：

- 遵循既有 Git 忽略及文件搜索规则；符合规则的隐藏文件可以纳入，并非一概忽略。
- 不跟随符号链接；二进制、无效 UTF-8、大于 2 MiB 及不可读文件会排除或报告。具体看状态。
- Python 语法解析失败时，保留可用文本，但不返回过期定义，并记录失败。空或仅含注释的语句块也可能是语法问题；文本命中不等于定义解析成功。
- 忽略规则不是访问控制。索引保存了源码文本，应按项目数据要求保护数据库与相关备份，不随意上传或公开。

删除仅清除该范围的索引，不动源码；之后仍可用其他工具开发，需要时再确认建库。数据库损坏时保留错误信息，经面板重建；不要将数据库错误改称“无命中”。

## 8. 企业日常操作与针对性排错 {#daily-work-and-troubleshooting}

推荐日常顺序：**进入正确项目与 profile → 首次 `/repo` 确认建立 → 自然语言提出任务 → AI 定位候选并读当前文件 → 调查与修改 → 按需测试。** 外部批量改动或切分支后，先按 `u` 完整核对再做依赖索引的调查；无需每次查询都重新建库。

- **提示没有索引：** 先核对 `Root:`、profile 和数据根，再确认建库；不必因此停止开发，可暂用 `read` / `grep` / `glob`。
- **代码明明存在却没命中：** 检查是否选错范围、`path` 过窄、被忽略或超限，再看覆盖状态；用当前文件和 `grep` 复核，不直接断言代码不存在。
- **Python 文本可查但定义没有：** 看解析失败与原始语法；若是旧解析记录，重建而非反复更新。非 Python 不期待符号解析。
- **一直未核对或待处理：** 查看原因和路径，判断是否仍有后台或外部改树活动，待稳定后完整核对；`status` 本身不会清掉这些状态。
- **续页报游标错误：** 检查是否换了条件或代次，重新从第一页查，不拼接旧、新结果冒充同一快照。
- **更新或重建很慢：** 看目标范围、进度、失败及文件系统状态；可取消。完整核对必须读取纳入文件，重建还需解析，不能把维护成本当成查询故障或承诺 NFS 提速。
- **损坏或不兼容：** `/repo` 按 `r` → `y` 恢复。删除重建前务必确认根目录，不手工清除源码。

## 9. 能力与性能边界 {#limits}

建库与查询使用本地 SQLite 和内置 Rust / Tree-sitter 解析能力，本身不调用模型或外部搜索服务；日常自然语言对话仍由当前选择的模型处理，不等于整场对话离线或不耗 Token。

文本通过 FTS5 trigram 等索引能力定位候选。已建库且没有已知待处理路径时，查询不必重复遍历源码；续页可复用绑定数据库、查询条件与代次的有界定位缓存，只加载当前页正文，不缓存整个源码树。并发维护期间可读取已发布旧代次，但未核对提示仍然有效。

代价是首次扫描、数据库磁盘空间、更新核对和解析维护。Repo **没有向量检索、调用图、依赖／影响分析、测试覆盖判断、配置消费推断或自动摘要**，也不是多人共享代码服务。它不等同于 `grep` 找全，不替代当前源码阅读和测试，不据本地行为推导公司实网、NFS 或所有版本的性能与验收结论。
