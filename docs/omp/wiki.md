# Wiki 企业知识库使用指南 {#wiki-guide}

Wiki 把已导出的企业 Markdown 资料保存为本地可检索知识库，供人直接查阅，也供 AI 查证后回答。适合内部规范、接口约定、设计方案、操作手册、故障判据和业务术语；它不是联网搜索，也不会自动抓取公司知识平台。

查当前项目的代码实现请用 [Repo](/omp/repo)，多人讨论方案可结合 [Team](/omp/team)。其他改动与优化见 [Fork 自有功能](/omp/features)，初次启动见 [OMP 入门](/omp/)。

## 1. 先准备资料与运行环境 {#prepare}

### 输入是什么 {#markdown-input}

准备一个可读的 Markdown 导出目录，例如 `/path/to/company-markdown`。导入递归读取 `.md` 文件，跳过符号链接；PDF、Word 等应先转换成 Markdown，可参考 [JchTools](/jchtools/)。

- 数据库保存完整 Markdown 文字、原始路径和行号，不只保存摘要或向量。
- 图片、附件、链接指向的页面不会随文字入库。Markdown 中有图片链接，不代表 Wiki 看过图片内容。
- 先检查导出范围、标题和正文是否完整，并保留原始资料及其版本说明。若正文只有链接，检索也只能得到这些文字。
- 只导入当前任务有权使用的资料；数据库本身同样是企业敏感正文的副本。

### 所有入口必须使用同一组设置 {#same-profile}

| 设置              | 应如何使用                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `OMP_CONFIG_ROOT` | 统一 OMP 数据根，必须使用绝对路径，支持 `~` 展开；相对值会被忽略。它同时影响 Wiki、会话、日志等，不只影响 Wiki。 |
| `-P work`         | 选择 `work` profile，注意大写 `P`。建库命令、删除命令和交互会话都要使用它。不同 profile 相互隔离。               |
| `OMP_OFFLINE`     | 内网离线模式通过环境变量启用，例如 `1`；没有 offline 命令行开关。CLI 与交互会话必须一致。                        |

Wiki 使用当前 profile 数据目录下的 `docs.db`，CLI、TUI、RPC 和 AI 工具共用这份数据库。**没有独立的 `OMP_WIKI_DIR` 配置**，遗留同名变量也不会改变位置。调整统一数据根不会自动迁移旧库。

以下以 Linux 的 tcsh 为例，在**系统终端**设置后，从同一环境启动 OMP；路径均须换成自己的已授权目录：

```tcsh
setenv OMP_CONFIG_ROOT /path/to/omp-data
setenv OMP_OFFLINE 1
omp -P work
```

普通非 offline 使用不设置 `OMP_OFFLINE`，但导入和会话仍要保持同一模式。Linux offline 的活动根与普通模式不同，不能认为同名 profile 在两种模式下必然看到同一活动库，详见[离线数据风险](#linux-offline)。其他 Shell 请使用对应的环境变量设置方式。

## 2. 首次建库：优先用面板 {#create-index}

在 **OMP 输入框**输入 `/wiki`，不是在系统终端输入。

1. 索引列表中按 `n` 新建。
2. 输入唯一索引名，例如 `company-docs`，按 `Enter`。
3. 输入导出目录，例如 `/path/to/company-markdown`，按 `Enter`。
4. 核对确认页的名称与目录，再按 `Enter` 开始；向导中按 `Esc` 返回上一步，第一步按 `Esc` 取消。
5. 等待导入完成，检查列表中的索引名、文档数、章节数和源目录。

同名已存在会报错，不会覆盖。只有全量导入成功后索引才公开可查；失败或取消不会留下可见半成品。导入进行时可按 `c` 或 `Esc` 取消。

### 系统终端的等价入口 {#cli-create}

如果更习惯命令行，在已经设置相同环境变量的**系统终端**执行：

```sh
omp -P work docs init "/path/to/company-markdown" --name "company-docs"
```

不使用自定义 profile 时，基本形式是 `omp docs init "<dir>" --name "<name>"`。不要漏掉正在使用的 `-P work`，否则可能建到了另一个 profile。

导入与检索均在本机完成，不调用模型，不需要模型凭据、向量服务、结构化提取或预设 schema。让 AI 根据检索结果组织答案则属于模型对话，是另一条数据使用链路。

## 3. 自己查：面板操作 {#panel-search}

| 所在位置／按键                                  | 动作                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| 索引列表 `↑` / `↓`                              | 选中需要查询的索引。面板只查这个索引。                             |
| `/`                                             | 输入关键词或自然语言问题，按 `Enter` 做默认相关性检索。            |
| `g`                                             | 输入正则表达式，按 `Enter` 做区分大小写的 grep。                   |
| 结果列表 `↑` / `↓`、`Enter`                     | 选择命中，打开完整存储正文。                                       |
| 正文 `↑` / `↓`、`PgUp` / `PgDn`、`Home` / `End` | 滚动正文；长行会折行，调整终端尺寸后仍可查看尾部。                 |
| 正文 `b`                                        | 返回当前页结果列表。                                               |
| 结果页或正文 `n`                                | 有下一页时继续取页；这里的 `n` 不是新建索引。                      |
| 忙碌时 `c` 或 `Esc`                             | 直接取消当前操作，不先等待关闭确认。                               |
| 空闲时 `Esc`                                    | 从结果／正文返回索引列表，再按可关闭面板；搜索输入中则返回原视图。 |

导入、列表加载、查询、续页、删除都会显示操作状态。取消或失败的续页保留原结果页及已选正文；不用为取消丢弃已有依据。关闭面板也会取消未完成操作。

## 4. 选择正确的检索方式 {#search-modes}

### 默认：技术相关性与完整名称 {#relevance}

按 `/` 后可以输入 `MBIST 仿真日志的检查项和判据`，也可以输入 `mbist_check.rpt` 或 `std::vector`。中文不需要手动分词。

默认模式基于 SQLite FTS5 全文检索，结合技术主题、连续词组、本节标题与相关性／BM25 排名。它不是布尔查询语言：没有布尔、引号或通配符语法，`AND`、`OR`、`*` 等按普通字符处理；也不会根据输入自动启用正则。

| 返回标记             | 该怎样理解                                                           |
| -------------------- | -------------------------------------------------------------------- |
| `match=exact-name`   | 完整技术名称证据，保留内部标点，名称匹配忽略大小写；优先于相关章节。 |
| `match=related`      | 主题或词元相关，不保证出现了所问的完整名称。                         |
| `未找到完整名称命中` | 没有完整名称证据，即使同时返回了相关章节也不能改称精确命中。         |

文件名、标识符、选项、路径等尽量保留原写法，例如 `foo_bar`、`--flag`、`ERR-123`。只命中更长名称的一部分不算完整命中，例如 `C++17` 不等于完整名称 `C++`。`exact-name` 是结果分类，**不是要输入的新命令或查询模式**。

### 显式 grep：查原始文字模式 {#grep}

按 `g` 可输入 `mbist_check\.rpt`，在数据库保存的原始 Markdown 中找对应字面名称。工具调用则明确设置 `mode: "grep"`。

- 面板 grep 区分大小写；AI 工具的 `case` 默认 `true`，设为 `false` 才忽略大小写。`case` 仅用于 grep。
- 正则使用 Rust 引擎，Rust 不支持的合法表达式交给 PCRE2；两个引擎均拒绝则报非法正则，不自动转成字面搜索。
- 按原始行匹配，不提供跨行模式、布尔查询语言或精确出现次数。`|`、分组与边界按正则引擎解释。
- 表达式首尾空格保留，超过 500 个 UTF-16 单元会报错；不要在复制时无意加空格。
- 只返回实际命中的章节，标记 `match=regex`，按索引、文档、章节的固定来源顺序分页，不混入相关章节。

默认检索适合“这项规范讲了什么”；grep 适合“原文哪些章节确实出现这个模式”。二者都只查已入库的资料。

## 5. 让 AI 查询、解释并引用 {#ask-ai}

退出面板，在 **OMP 普通对话输入框**提交：

```text
用 wiki 查询 MBIST 仿真日志的检查项和判据。取完相关结果的全部页，
按索引名、文件路径、行号和文档版本标注依据；区分明确规定与推断。
如果只有相关章节而没有完整名称命中，请明确说明；缺少依据不要补写规定。
```

AI 的 `wiki` 是只读查询工具，搜索全部已导入索引，不替用户新建或删除索引。面板只查所选索引，因此两者结果范围可能不同。

以下是 **AI 工具参数**，不是系统终端命令，也不是需要粘贴到 `/wiki` 面板的内容：

```json
{ "query": "MBIST 仿真日志" }
```

显式正则、忽略大小写的工具参数示例：

```json
{ "query": "mbist_check\\.rpt", "mode": "grep", "case": false }
```

默认按需设备模式下，AI 先用 `read xd://wiki` 获取说明和 schema，再由 `write xd://wiki` 携带上述 JSON 查询；这里的 `write` 是设备传输入口，不会把 Wiki 查询变成写库。其他工具配置下也可能直接显示顶层 `wiki` 工具，查询语义仍相同。

### 续页必须保持同一次查询 {#pagination}

页脚会显示命中章节总数，并给出下一次调用参数，或明确说明结果已耗尽。工具常规每页目标约 8000 字符、最多 200 节；每页首节即使超长也完整返回，不因页预算截断正文。

1. 有下一页时，让 AI 原样使用页脚提供的有效 `query`、`cursor` 及检索选项。
2. 保持模式、grep 大小写选项和索引范围，不要改问题来冒充续页。
3. 直到明确耗尽才表示取完；重复正文可能指向同页完整文字，但每个来源仍保留，跨页重新提供完整正文。

例如首次返回续页参数后，后续形如下面这样调用；游标必须使用实际返回值，不能自行构造：

```json
{ "query": "MBIST 仿真日志", "cursor": "实际返回的游标" }
```

默认 search 的超长查询会在超过 500 字符时截断并带省略号，续页应复制返回的**有效 query**，而非重新粘贴原长问题；grep 超长则报错，不做相同截断。

游标绑定查询、模式、有效大小写选项、索引范围和数据库逻辑版本。导入、删除或其他数据库变化可能令旧快照过期：此时不带 cursor，用原查询重新开始，不能把新结果接在旧页后当作同一快照。版本不变时，服务关闭重开不应单独使有效游标失效；损坏或不匹配游标是错误，不是零命中。

## 6. 把证据变成可靠答案 {#evidence}

每条命中包含索引名、相对路径、行号、文档 SHA-256 和 `sectionId`。引用应保留“索引名＋路径＋行号＋文档版本身份”，例如说明“依据 `company-docs` 中某文件的导入版本”，并沿用实际返回的哈希，不能编造。

- 同名路径可能来自不同索引；只有路径不够区分来源。
- 路径与行号对应**导入时版本**，不保证与今天源文件一致。`sectionId` 在删除后重建可能复用，不能当永久引用。
- 正文冲突时列出各自依据和版本，不凭相关性排名认定哪个是现行制度；历史资料不自动代表最新规范。
- `0 matches` 是已有可查询索引下的正常成功，只说明“本次检索的已导入语料中没有匹配”，不证明公司不存在相关规定。

实际数据流程是：**导出 Markdown → 导入完整正文与来源 → 从数据库检索和续页 → 人或 AI 按返回证据引用**。导入成功后，查询、续页与引用全部 DB-only，不回读源文件，不检查新鲜度，也不自动同步；即使源目录移走仍可查询，但这不是源资料备份完整性的保证。

## 7. 资料更新：删除旧索引后重新导入 {#refresh}

先完成新导出，确认目录可读、内容完整，并核对数据根、offline 模式、profile 和索引名。不要拿共享生产数据练习删除；存在其他使用者时先协调维护窗口。

在**系统终端**按顺序执行，第一步成功后再执行第二步：

```sh
omp -P work docs remove "company-docs" --force
omp -P work docs init "/path/to/company-markdown" --name "company-docs"
```

也可以在 `/wiki` 索引列表选中旧索引，按 `d`、再按 `y` 确认删除；按 `n` 或 `Esc` 放弃删除。删除后按新建流程重新导入。

**删除只删当前 profile 数据库中的索引，不删源文档，也不删除其他 profile 的索引。** 但旧索引删除到新索引发布之间会缺库；若重新导入失败，旧索引不会自动恢复，因此不要先删再准备资料。

维护 CLI 只有 `init` 和 `remove`。没有 `omp docs update`、`list`、`status` 或 `rebuild` 命令；看已有索引用 `/wiki`。不要把 Repo 的维护方式套到 Wiki 上。

## 8. 性能、取消与 Linux offline 数据风险 {#runtime}

查询内核使用 Rust，SQLite 查询连接默认请求最多 500 MiB 的 mmap 读取，由操作系统按需复用数据库文件页面；这不是单进程或整机内存硬上限，也不是每个进程额外分配 500 MiB 堆内存。

同一未变化查询的完整匹配排名会被有界缓存，续页主要读取本页正文和来源，不必每页重新全库扫描和排序。缓存淘汰不应丢掉证据尾部，数据库变化后则不能复用陈旧快照。不要据此承诺固定加速倍数。

查询与索引操作不在交互线程执行数据库工作，可取消，界面仍应能接收输入。每次**成功**搜索，包括续页和合法零命中，对外总时长**不少于 500ms**；不足时异步等待补足，等待也可取消。这是下限，**不是 500ms 内完成的响应承诺**。错误和取消不补等待时间。

### Linux offline 要特别注意 {#linux-offline}

仅 Linux 且 offline 启用时，Wiki 等 OMP 自有活动数据进入 `/dev/shm` 运行根。`OMP_CONFIG_ROOT` 仍表示原始持久根和备份目标，不应手动改成临时 shm 路径；profile 继续在统一运行根内隔离。

- 前台就绪满 10 分钟才首次异步备份，之后每 10 分钟触发；不是启动时先复制旧库。
- 启动不从持久根复制或恢复，shm 为空时就是新环境。切换主机或重启后，旧索引不保证自动出现，需要按运维流程人工恢复。
- 退出不等待最终备份。未成功备份的变更、运行不足一个周期的短命导入命令，不保证已经持久化；shm 丢失可能丢失这些数据。
- 此机制不是透明磁盘缓存，不应据此假定 NFS 多机并发安全；非 Linux 或非 offline 不启用该映射及备份。

## 9. 常见问题与隐私边界 {#troubleshooting}

| 现象               | 先检查什么                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| 刚导入却看不到索引 | CLI 与会话的 `OMP_CONFIG_ROOT`、`-P`、offline 模式是否一致；导入是否完整成功；Linux shm 是否为空。 |
| 同名建库失败       | 名称必须唯一，不会覆盖。若确实刷新，先确认可接受缺库窗口，再按 remove → init 操作。                |
| 有库但零命中       | 导出范围是否含目标正文、图片是否尚未转文字；换技术名称或正确模式重查，不下“没有规定”的结论。       |
| grep 报错          | 检查正则语法、转义、长度与首尾空格；无匹配本身不是非法正则。                                       |
| 游标错误／过期     | 不修改参数续接；复制正确页脚参数，数据库已变则不带 cursor 重新开始。                               |
| 源文件改了答案没变 | Wiki 不同步源文件，需重新导出后 remove → init；先核对引用的文档哈希。                              |
| 无索引／数据库故障 | 这是错误而非零命中。核对运行位置、存储可用性及操作错误信息，不用删除共享库试错。                   |

导入和检索不调用模型，**不等于之后的 AI 回答不会把检索正文发送给所选模型服务**。先确认企业允许的模型、资料范围和使用权限；offline 限制公网发现及相关能力，但公司内部模型请求仍可发生，并非“所有网络请求被禁止”。

保护源导出、`docs.db`、备份、导出的查询结果及含证据的会话，分享故障材料时脱敏路径与正文。删除索引不会自动清理其他副本或已有会话。本文说明当前功能用法，不代表公司实网、所有发布版本或 Linux／NFS 环境均已验收。
