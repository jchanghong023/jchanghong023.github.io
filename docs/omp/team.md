# Team 使用与编排指南 {#team}

`/team` 把一个问题交给多个独立 Agent 调查、互相审查，再形成有依据的方案。适合需求澄清、问题诊断和架构取舍；**只做分析与规划，不负责实施，也不是无人值守改代码命令。**

企业资料先看 [Wiki 指南](/omp/wiki)，代码定位先看 [Repo 指南](/omp/repo)；其他改动与优化仍在 [Fork 自有功能](/omp/features)。

## 一、第一次怎么用 {#first-use}

### 第 1 步：进入项目，准备资料 {#prepare}

在要分析的项目目录启动 OMP。使用与日常工作一致的 Profile、数据根和网络模式，不要为了 Team 临时换一套目录。

- 有需求文件时，给出明确、可访问的路径；示例中的文件必须真实存在。
- 需要查企业规范时，先按 [Wiki 指南](/omp/wiki)导入 Markdown 资料；Team 不负责导入或刷新知识库。
- 需要借助代码索引时，先按 [Repo 指南](/omp/repo)确认项目根并建库。没有索引也可以阅读、检索源码，但不能冒称已经核实缺失的规范。
- **不要只发图片。** Team 子代理不接收提交中的图片，应提供可读取的文字说明或资料路径。

### 第 2 步：选负责综合的主模型 {#main-model}

在 OMP 输入框按 **Ctrl+T**，选当前会话模型。它负责第 2 阶段的对齐和第 5 阶段的综合，建议选你认为综合判断能力最好的可用模型；程序不会自动评选“最强模型”。

**第一次不用配置成员名单。** `team.members` 未设置或为空时，当前模型会创建三个独立提案 Agent；红区和普通启动都遵循这条规则，不会自动换成公司模型组合。

当前模型和所有参与模型都必须可用，并支持只读工具与结构化输出。`jchtools/…` 这类由后端 Agent 执行工具的通道不支持 Team，主模型也不能选它。黄区的 `codeagent/…` 与 `jchtools/…` 不是同一种通道，使用前仍以当前版本的能力检查和真实调用结果为准。

### 第 3 步：提交一个完整问题 {#submit}

以下内容发在 **OMP 输入框**，不是系统终端。替换资料路径；若没有需求文件，就把需求直接写进正文。

```text
/team 阅读 docs/requirements/api.md，结合现有代码和已导入的 Wiki，比较接口缓存的改造方案。必须保持现有返回顺序和错误行为，不增加部署依赖。给出源码或文档依据、主要取舍、未验证前提、执行前检查和验收标准。只做规划，不实施。
```

最好一次说清四件事：**目标、资料入口、不能改变的约束、希望拿到的结果**。只输入 `/team` 会提示补充问题，不会替你猜任务。

也可以直接用于诊断：

```text
/team 当前接口偶尔返回重复结果。只读调查相关实现和测试，区分已确认原因与待验证假设，给出证据和下一步核查方法，不修改文件。
```

### 第 4 步：等待编排，查看状态 {#observe}

启动提示会给出本次后台任务 ID、独立提案 Agent 数和不同模型数。记住**本次 Team 的任务 ID**，需要取消时用它定位整项讨论。

- 当前阶段与完成、失败状态显示在现有任务状态区域。
- 输入 `/hub` 打开 Agent Hub，可查看子代理与转录；不用手工建团队、转发原稿或催各 Agent 对齐。
- 运行中不会中断流程向你提问；查不清的事实与有歧义的需求会保留到结果中，而不是猜成已确认信息。
- 不要中途切换或恢复到另一个聊天会话来“让它继续后台跑”：当前 Team 绑定发起会话，成功切换到另一会话会取消原任务。

### 第 5 步：看结果，不把推荐当验收 {#read-result}

最终报告以一条 Markdown 消息回到当前会话并保存，不自动生成项目方案文件，也不自动创建 Todo。

先看有没有置顶的需求理解差异、流程未完成或“尚不可采用”；再看方案的依据、风险和执行前检查。**流程完成不代表必须有赢家；有推荐也不代表代码或性能已经验证。**

### 第 6 步：澄清，或另行授权实施 {#handoff}

- 想理解取舍，可以直接追问：“方案 A 为什么比 B 更适合当前约束？”这是普通聊天，不会自动重跑整场讨论。
- 存在影响选择的需求歧义时，先给出答案，再携带原问题和澄清内容重跑 `/team`，不要在不同前提的方案之间盲选。
- 回复“选择方案 A”只确认方案、验收标准与执行前检查，**不授权改代码**。
- 确定实施时，另发明确任务，例如：

```text
按本次 Team 的方案 A 实施。先核实报告列出的执行前条件，条件不成立就停止并报告；仅修改当前仓库相关模块，保留无关改动，按项目规则验证。未经另行授权不要提交或推送。
```

需要无人值守执行时，先确认范围和授权，再参照[无人值守 Goal](/omp/features#goal)；它不是 Team 讨论流程的一部分。

## 二、成员和并发怎么配置 {#members}

### 不配置也能用，多模型是可选项 {#member-rules}

`team.members` 是**有序的模型名单**，不是 `/model` 中的 default、plan 等角色。显式设置后，只使用这份基础名单，不自动把主模型追加进去；主模型仍独立负责对齐与综合。

设基础名单有 `M` 项，提案 Agent 数为 `max(3, M)`，从名单开头循环分配。重复项也占一个位置，不去重；每个位置都有独立上下文和标签。

| 基础名单（字母代表模型） | 提案 Agent 使用的模型 |
| ------------------------ | --------------------- |
| 未配置，当前模型为 A     | A、A、A               |
| A、B                     | A、B、A               |
| A、B、C                  | A、B、C               |
| A、B、C、D               | A、B、C、D            |
| A、A、B                  | A、A、B               |

三个 Agent 不等于三种模型，更不等于总共只调用三次模型：后续还会新建对齐、审查、修订、复核和综合子调用，因此耗时与用量高于一次普通问答。

### 修改名单的实际入口 {#configure}

默认方案足够时跳过本节。确需指定成员时，先在**系统终端**查看可用模型、当前名单和配置目录：

```sh
omp models
omp config get team.members
omp config path
```

这些命令要与目标会话使用相同的 `OMP_CONFIG_ROOT` 和 Profile。会话使用 `-P work` 时，命令也使用相同的 `-P work`，不能把另一 Profile 的结果当成当前配置。

在 `omp config path` 所示目录下的 `config.yml` 中，**合并**以下字段，不要用这段内容覆盖整份文件。把占位模型 ID 替换为 `omp models` 中实际可用的完整 ID；也可明确让 Agent 代为设置并检查结果。

```yaml
team:
  members:
    - provider-a/model-a
    - provider-b/model-b
```

保存后重新启动目标 OMP 会话，用 `omp config get team.members` 核对有效配置；项目或启动配置覆盖仍有优先级。清空名单或移除此项可恢复默认的“当前模型三个提案 Agent”行为；如果有覆盖层，需在实际生效的那层调整。

`task.maxConcurrency` 限制同时运行的子代理数。超出时排队，**不会砍掉成员或省略提案**；名单加长意味着工作量增加，不保证更快或更正确。

### 阶段 1：多个 Agent 各自调查 {#investigate}

编排器按成员槽位创建独立提案子代理，交给它们**相同的用户问题、约束与资料入口**，但不共享调查摘要，也看不到其他代理的原稿。

每个 Agent 自己读需求、在可用时优先查 Wiki 和 Repo，再读当前源码和接口，提出方案或诊断结论，记录证据、假设、风险、未知项与验收建议。同一模型的三个 Agent 也必须各查一遍，不能由一个人调查、另外两个复述。

产物是每个槽位的结构化提案。指定资料缺失、位置不明或关键调查受阻时，会说明原因；“调查未完成”不能包装成“分析完成但无解”。

### 阶段 2：主模型对齐问题，不先决定赢家 {#align}

编排器用当前会话模型创建一次对齐子调用，输入原问题和全部提案，整理三类材料：

- **共同目标与验收标准：** 大家必须在同一套要求下比较，不能各自选择容易满足的标准。
- **事实差异：** 例如接口是否存在、当前代码是否已处理某个边界，标出需要回查的位置。
- **需求理解差异：** 例如“保持兼容”到底指哪一类行为；无法由资料消除的差异保留下来。

这个阶段不向用户提问、不强行达成共识。对齐后的摘要不能增加、删除或放宽用户原要求及已确认适用的强制约束。

### 阶段 3：为每份候选安排新代理审查 {#review}

每份拟作为最终选项的方案安排一名**新的审查子代理**，不是让作者自评。编排器按槽位顺序轮转到下一个不同模型；全是同一模型时，用该模型的新上下文。

审查者拿到原始要求、适用约束、共同验收标准、方案、假设和资料入口，可回查 Wiki 与代码；提示词不显示作者模型名、支持人数或推荐顺序，减少身份与从众偏差。

审查重点是事实错误、需求遗漏、不成立的前提、兼容风险，以及能否满足验收。意见分为阻断、重要、次要，必须说清依据与影响；允许“未发现实质问题”，但这不等于已验证绝对正确。

### 阶段 4：逐问题回应，需要时由新代理复核 {#revise}

编排器为有效审查中的问题分配稳定 ID，例如 `A-F1`，把最新意见与仍未解决的阻断交给该方案的**原提案模型、新上下文**处理。

1. 修订者逐 ID 回应：接受并修改、举证反驳、保留真实取舍，或承认未解决。只写“已修复”不能关闭问题。
2. 若改了核心设计、接口或兼容策略，声称解决严重问题，以新证据改变关键前提，或反驳已有阻断，代码会触发新的审查代理复核；没有这些变化时不强凑复核。
3. 复核者逐条裁决未决阻断，给出已解决或未解决及依据。**作者不能自行关闭阻断**，“没发现新问题”也不能清掉旧问题。
4. 每份方案最多两轮“修订与必要复核”。复核失败、缺失或格式不合法也占用轮次；历史问题与待核实修订不会被抹掉。

两轮后仍有阻断或必需复核未完成，方案标为**尚不可采用**。达到轮数上限不是通过，也不会自动重开讨论来绕过限制。

### 阶段 5：主模型核实证据，给出可选择的结果 {#synthesize}

编排器再用当前会话模型创建综合子调用，输入原问题、共同标准、最新方案、完整审查与修订回应、复核结果及未决问题。

综合先检查硬约束和阻断，再比较正确性、风险、复杂度、兼容性、修改范围和维护成本。**不是多数票；不能因为更省事就忽略正确性，也不能临时拼出未经审查的新方案。**

有明确优势才给出推荐和成立前提；只有一个可采用方案就只给一个，全都不可采用就解释原因。存在影响选择的需求理解差异时，结果置顶提示先澄清再重跑。

程序按问题 ID 维护的状态高于模型在正文中的乐观表述，不能把尚有阻断的方案说成已通过。有效报告持久写回发起会话后才算交付；不会因完成讨论自动启动实施。

## 四、如何读最终报告 {#report}

按以下顺序检查即可，不必逐份阅读全部中间原稿：

1. **流程状态与理解差异：** 是否完成必要调查与审查？是否因资料、模型失败而未完成？是否要先回答歧义？
2. **需求与共同验收：** 是否忠实覆盖你的原始要求、兼容限制和实际完成条件？
3. **方案与证据：** 改什么、影响哪里，关键判断能否回查具体文档或源码？
4. **阻断与未验证前提：** 哪些问题仍未决？执行前要通过什么观察区分“成立、被反驳、仍不确定”？
5. **推荐与取舍：** 推荐依赖什么条件，为什么比其他候选更合适？没有推荐并不一定是流程失败。

方案中的性能数字、根因和验证方法，要区分**已经观察到的事实、推断、预期和待验证项**。讨论过程不运行构建或测试，不能将设计审查结论当成产品验收。

## 五、如何取消与处理失败 {#cancel}

### 取消整项讨论，不只是一个子代理 {#cancel-run}

按启动消息记录的 Team 后台任务 ID，通过现有后台任务取消入口（启动提示中的 `hub cancel`）取消**整项 Team 任务**。它是任务控制能力，不要把 `hub cancel` 当成系统终端命令。

也可在 OMP 主会话明确要求：

```text
取消刚才启动的 Team 后台任务，使用启动提示中的任务 ID，通过后台任务取消入口执行，确认整项讨论已经停止，不只是终止一个子代理。不要继续调查或重新发起讨论。
```

**普通 `Esc` 不表示整项讨论已取消；只终止一个子代理也不等于取消编排。** 正确取消会传播到所有在跑子代理，不再进入后续阶段；应核对后台任务的取消或终止状态，不能仅以不再刷新判断停止。

### 常见异常怎么处理 {#errors}

- **模型不可用或能力不支持：** 先修正主模型或 `team.members`，不会静默剔除成员后继续。
- **某个提案、审查或修订失败：** 标明参与不完整，不自动重试或找人替补；其余可继续处理，失败不是赞同。
- **关键调查受阻、对齐或综合失败、必要审查无法完成：** 报告流程未完成，不交付伪装成完整结论的半成品。
- **Wiki 没命中关键约束：** 补充资料或修正检索范围，不能据此认定企业规范不存在。
- **资料、需求或约束已经变化：** 带上更新后的完整问题重跑，不沿用旧版的推荐与通过状态。

## 六、只读、隐私与适用范围 {#boundaries}

提案、对齐、审查、修订、复核和综合子代理都由代码限制为只读工具：读取文件、`grep`、`glob`、Wiki、Repo、只读 AST 检索及结构化提交。能查哪些工具，仍受其启用状态和访问权限限制。

**不能写项目、运行 bash/eval、安装依赖、构建测试、管理索引、提交或推送。** 方案“修订”只改讨论材料；正常会话与结果记录仍会保存。Repo 的只读查询可能按已有规则维护已知变动，不代表子代理获得了索引管理权限。

多个 Agent 会读取任务所需的企业资料并向所选模型提供上下文。只在获准的模型、网络和项目范围内使用；本机索引不意味着后续模型请求完全离线，讨论记录也需按企业资料保护。
