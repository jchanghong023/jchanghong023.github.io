# 先探索 {#explore-1}

**`/opsx:explore` 是你的思考伙伴。只要你有问题但还没有方案，就该用它。** 它会在写下一行代码之前，先调查你的代码库、与你一起权衡各个选项，并厘清你真正想要的东西。当图景清晰之后，它会交接给 `/opsx:propose`。

如果你要从这些文档中带走一个习惯，就带走这个：**当你还不确定时，先探索，再 propose。**

为什么这很重要？AI 编程助手很急切。你含糊地提问，它会自信地造出*某个东西*，只是可能并不是你需要的那个东西。探索就是解药。它是一场零风险的对话，让你和 AI 一起找到正确的做法，这样等到你 propose 时，propose 的就是正确的东西。

## 何时探索 {#explore-2}

探索作为第一步的适用场合，比人们预想的要多得多。只要满足以下任一条件，就使用它：

- 你知道*问题*，但不知道*解决方案*。（"页面感觉好慢。""鉴权一团乱麻。""我们老是收到重复订单。"）
- 你正在几种方案之间选择，想要结合你实际的代码把各种取舍摆出来。
- 你刚接触一个代码库，需要先弄懂某处是怎么工作的，再去改它。
- 需求还很模糊，你想在投入之前把它们理清楚。
- 你怀疑这项工作的规模比看起来更大或更小，想要诚实地界定范围。

只有当你已经完全清楚自己想要什么、以及该怎么做时，才跳过探索。那种情况下直接去 [`/opsx:propose`](commands.md#opsxpropose)。

## 它做什么（以及不做什么） {#explore-3}

探索是一场**对话**，不是生成器。

**它会做：**

- 读取并搜索你的代码库，回答真实的问题。
- 比较各种选项，并说出每个选项的取舍。
- 画图让设计变得清晰可读。
- 帮你把模糊的想法收窄成具体、可构建的范围。
- 在你要求时、或在你接受它的提议时，捕获这次探索：它用 `openspec new change` 搭建 change 骨架，并写出你点名的规划 artifact，或者更新某个已有 change 的 artifact。
- 在你准备好时，过渡到 `/opsx:propose`。

**它不做：**

- 写代码或改代码。探索在任何情况下都不写代码，捕获场景也不例外。
- 设计或编辑你的 schema 或模板。塑造这些东西本身就是一个 change，而不是思考。
- 自行启动 change 或写出 artifact。除非你要求，或者它提议时你表示同意，否则它什么都不写；即使写，也只写你同意的那部分，外加启动一个 change 所需的设置文件（见下文）。
- 催你去捕获。当思考成形时它会提议，由你来决定。

这正是重点所在。探索不花你任何东西，也不会让你承诺任何东西，直到你开口为止。你可以探索三条死路，从每条中学到东西，然后才 propose 那条活下来的路径。

## 它已经装好了 {#explore-4}

好消息：`/opsx:explore` 包含在默认的 **core** profile 里，与 `propose`、`apply`、`update`、`sync`、`archive` 并列。你不需要启用任何东西。如果你的项目已经配置好 OpenSpec，探索就在你的 AI 聊天里待命。（与所有 `/opsx:*` 命令一样，你是在助手的聊天里输入它，而不是终端。参见 [How Commands Work](how-commands-work.md)。）

## 一个完整示例 {#explore-5}

看看一个模糊的担忧如何变成一个精准、可构建的 change。

```text
你：/opsx:explore

AI：你想探索什么？

你：我们的结账流程有时会创建重复订单。我不知道原因，
    也不知道怎样安全地修好它。

AI：让我深入看看结账路径……
    [阅读订单服务、支付 webhook 处理器，以及
     客户端提交逻辑]

    这是我发现的情况。重复订单有两种产生方式：

    1. 客户端可能提交两次（双击、网络慢时重试）。
       没有任何防抖处理。
    2. 支付 webhook 可能触发不止一次，而处理器
       每次都创建一个订单。没有幂等键。

    第 2 种原因是危险的那个：它可能重复扣款并重复履约。

    有三种修法，大致按健壮性排序：
    - 在创建订单的端点上加幂等键（同时解决两种原因）
    - 在 webhook 上按 payment-intent id 去重（只解决第 2 种）
    - 客户端防抖（只解决第 1 种，且掩盖了真正的 bug）

    鉴于你的代码已经存储了 payment-intent id，
    幂等键方案改动小、收益最大。
    要我把这个范围界定出来吗？

你：好，我们就做幂等键。

你：/opsx:propose add-order-idempotency-key

AI：已创建 openspec/changes/add-order-idempotency-key/，其中包含 proposal
    和基于我们刚才发现的内容写成的 delta spec。可以开始实现了。
```

注意刚刚发生了什么。起点是"有地方出错了，我不敢碰"。二十秒的探索把它变成了一个有名字的根因、三个排好序的选项、一条结合现有代码给出的建议，以及一个精确的 change。随后产生的 proposal 之所以精准，是因为思考发生在前面。

## 交接给 propose {#propose}

探索不会归档到任何地方。当你准备好时，直接启动一个 change，AI 会把你对话中的上下文带进 artifact。

```text
explore  ──►  propose  ──►  apply  ──►  archive
 (思考)       (达成一致)    (构建)      (记录)
```

你可以用大白话说明（"把这个变成一个 change 吧"），也可以直接运行 `/opsx:propose <name>`。无论哪种方式，你刚刚完成的探索都会成为 proposal 的基础，而不是用完即弃的聊天记录。

你也可以让探索在不离开对话的情况下捕获这个 change 本身："为这个启动一个 change"会搭好文件夹骨架，"顺便写 proposal 吧"只会写出你点名的那些 artifact。搭建骨架时还会写入该 change 自身的元数据，并在顶层补齐你项目缺失的内容（`openspec/specs/`、`openspec/changes/archive/`、`config.yaml`）。

这与交接是同一个目的地，只差一点：propose 会写全你的 schema 要求达到可实施状态所需的整套 artifact，而捕获只写你点名的那些 artifact。

如果你使用扩展命令集，探索也可以改为交接给 `/opsx:new`，以便逐个创建 artifact。参见 [Workflows](workflows.md)。

## 一次好探索的提示 {#explore-7}

- **带来问题，而不是解决方案。**"登录感觉好慢"给 AI 留出了调查空间。"加一个 Redis 缓存"则提前让你锁定了一个还没验证过的答案。
- **把取舍大声问出来。**"每个选项的缺点是什么？"能让你得到更诚实的比较。
- **先让它读。**最好的探索始于 AI 真正去看你的代码，而不是猜。如果有帮助，把它指向相关区域。
- **中途退出也没关系。**如果探索揭示出这个想法不值得做，那就是胜利。你以很低的代价学到了这一点。
- **在 change 进行中再次探索。**在 `/opsx:apply` 期间卡住了？你可以退回来探索一个子问题，然后再回去。

## 诚实的取舍 {#explore-8}

**你得到什么：** 探索能在代价最低的时刻抓住错误的方向，也就是在你做出任何承诺之前。它在外来代码中尤其强大——AI 阅读并总结系统的能力，能帮你省下一整个下午的摸索。

**你付出什么：** 一点耐心。探索是一场对话，所以它比直接抛出 `/opsx:propose` 然后祈祷要慢。对于那些你确实已经理解透的工作，这一步是纯粹的开销，你应该跳过它。

经验法则：任务越模糊，探索的回报越大。任务越清晰，你越可以直接去 propose。
